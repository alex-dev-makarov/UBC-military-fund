# Безпека проєкту: що зроблено, як і чому

Навчальний документ. Для кожного прийому тут пояснено, від чого він захищає,
як працює і де лежить у коді. Довідник «як підтримувати» — у
[telegram-auth.md](telegram-auth.md).

---

## 0. Модель загроз: з чого починається будь-яка безпека

Перш ніж захищати, треба відповісти на три питання.

**Що захищаємо?** Імена людей і суми допомоги. Якщо вони витечуть, можуть
постраждати реальні люди. Це найцінніше в системі, тому все інше будується довкола них.

**Від кого?**

| Хто | Що може | Що робимо |
|---|---|---|
| Будь-хто з інтернету | Відкрити сайт, слати запити до API | Без входу через Telegram дані не віддаються ніяк |
| Колишній член церкви | Мав доступ, вийшов з каналу | Членство перевіряється на **кожен** запит |
| Шахрай | Обманом змусити члена церкви «натиснути кнопку» | Вибір числа з сайту, повідомлення «Новий вхід / Це не я» |
| Член церкви, який зливає | Зробити скрін | Заборонити неможливо, тож робимо витік відстежуваним |
| Той, хто має доступ до сервера | Змінити журнали, щоб замести сліди | Тригери в базі |
| Помилка розробника | Закомітити секрет, вимкнути HTTPS | Перевірки в коді, які не дають запуститись із поганим конфігом |

**Принцип «fail closed»** («при збої — зачиняй»). Якщо щось пішло не так
(Telegram не відповідає, змінна не задана), система **відмовляє** в доступі, а не
пропускає. Цей принцип повторюється в усьому проєкті.

## 1. Вхід через Telegram

### 1.1 Базова ідея: nonce і deep link

**Nonce** (number used once) — випадковий одноразовий рядок. Сайт просить
сервер створити nonce і відкриває `t.me/<бот>?start=<nonce>`. Коли людина
натискає Start, бот отримує цей nonce і знає, що це «та сама» спроба входу.

- 32 випадкові байти (`crypto.randomBytes`): вгадати неможливо.
- Живе 5 хвилин і використовується один раз.
- Стани: `pending` → `confirming` → `authorized` / `denied`.
- Кожен перехід — **атомарний** `UPDATE ... WHERE status = 'попередній'`. Два
  одночасні запити не можуть обидва «виграти». Це захист від *race condition* (гонки).

Код: `api/src/entities/login-session/api/nonce.repository.ts`

### 1.2 Атака «підміна входу» (login fixation) і чому потрібне число

Без додаткового кроку можлива така атака:
1. Зловмисник натискає «Увійти» у **своєму** браузері й отримує посилання на бота.
2. Пересилає його члену церкви: «натисни Start, там новий звіт».
3. Член церкви натискає. Бот бачить, що це учасник каналу, і підтверджує вхід.
4. Сесію забирає **браузер зловмисника**. Ще й журнал вказує на члена церкви.

**Захист 1 — вибір числа (number matching).** Сайт показує двозначне число
тому, хто почав вхід. Бот показує три числа кнопками, і треба натиснути те, що на
сайті. Член церкви, якого обманули, сайту не бачив, тож не знає, яке правильне.
Неправильний вибір скасовує спробу назавжди. Так само працюють банківські
застосунки й Microsoft Authenticator.

> Межа: навмання можна вгадати з шансом 1 до 3. Для закритого чату, де всі знають,
> хто розсилає посилання, цього достатньо. Якщо колись знадобиться суворіше, можна
> попросити людину **ввести** число в бота (тоді шанс 1 до 90).

**Захист 2 — прив'язка до браузера (binding cookie).** Під час старту сервер
ставить браузеру `httpOnly`-cookie з випадковим значенням, а в базі зберігає
лише його **хеш** (SHA-256). Забрати сесію (`/poll`) може тільки браузер із цією
cookie. Тож навіть якщо nonce витече (скрін, лог), чужий браузер нічого не отримає.

**Захист 3 — «Це не я».** Після входу бот пише: «✅ Новий вхід: Chrome · Windows,
14:05» з кнопкою **«Це не я — вийти всюди»**. Якщо шахрай таки вмовив людину
ввести число, вона побачить чужий пристрій і одним натисканням:
- завершить усі свої сесії;
- скасує незабрані входи;
- «спалить» невикористані посилання.

**Захист 4 — текст-попередження** в боті: «Якщо ви не входили на сайт щойно — нічого не натискайте».

Код: `api/src/features/auth-telegram/model/bot-updates.service.ts`,
`api/src/features/auth-telegram/model/login-code.ts`

### 1.3 Членство перевіряється завжди

`getChatMember` питає Telegram, чи людина зараз у каналі. Це відбувається:
- коли людина натискає Start;
- на **кожному** запиті до закритого звіту (`MEMBERSHIP_TTL_SEC=0` — без кешу).

Вийшов з каналу — наступний запит отримає 403. Якщо Telegram не відповідає,
сервер повертає 503 (fail closed), а не пропускає.

**Single-flight.** Якщо одна людина робить 5 запитів одночасно, у Telegram іде
**один** запит, а решта чекають його відповіді. Так бот не впирається в ліміти
Telegram і не можна «завалити» його зсередини.

Код: `api/src/entities/user/lib/channel-member.guard.ts`

## 2. Сесії

### 2.1 JWT у cookie

Після входу сервер видає **JWT** (JSON Web Token): підписаний рядок «ця людина
— Telegram ID 123, видано тоді-то». Підпис (`HS256` + секрет) не дає його підробити.

Токен лежить у cookie з прапорцями:

| Прапорець | Що дає |
|---|---|
| `HttpOnly` | JavaScript сторінки не може прочитати cookie, тож XSS не вкраде сесію |
| `Secure` | Cookie йде лише по HTTPS (на dev/prod це обов'язково) |
| `SameSite=Lax` | Інші сайти не можуть надіслати POST із твоєю cookie (захист від CSRF) |
| префікс `__Host-` | Браузер **сам** гарантує: тільки HTTPS, тільки цей хост, без `Domain`. Піддомени cookie не бачать |
| `Max-Age` = строк JWT | Cookie й токен живуть однаково (15 хв на проді) |

### 2.2 Токен прив'язаний до оточення

JWT підписується з `iss=ubc-dev` або `iss=ubc-prod` і перевіряється так само.
Якщо хтось випадково поставить однаковий `JWT_SECRET` на dev і prod, dev-токен
на проді все одно не прийметься.

### 2.3 Як «завершити» JWT, який ще не прострочився

JWT неможливо «стерти» в чужому браузері. Тому в таблиці `users` зберігається
`sessions_valid_after` — мітка часу в мілісекундах. Токен, виданий **раніше** за
неї, вважається відкликаним (`SessionValidGuard`). Її ставлять:
- кнопка «Вийти» на сайті;
- кнопка «Це не я» в боті;
- адмін командою з `telegram-auth.md`.

> Чому мілісекунди? Стандартна мітка `iat` у JWT — у секундах. Токен, виданий у
> ту саму секунду, що й відкликання, «виживав». Тепер у токені є власне поле
> `iat_ms`, і порівняння точне.

Код: `api/src/entities/user/lib/session-valid.guard.ts`,
`api/src/entities/user/api/user.repository.ts`

### 2.4 Порядок перевірок на закритому звіті

```
JwtAuthGuard → SessionValidGuard → RateLimitGuard (на людину) → ChannelMemberGuard
  підпис ок?     не відкликано?       не забагато?               ще в каналі?
```
Дешеві перевірки стоять першими, а дорога (запит у Telegram) — остання.

## 3. Захист запитів

### 3.1 CORS і Origin

**CORS** вирішує, з яких сайтів браузер дозволить JavaScript читати відповіді
нашого API. У нас лише наші домени (`FRONTEND_ORIGIN`).

Але CORS не забороняє **надсилати** запити. Тому для дій, що змінюють стан
(старт входу, handoff, вихід), сервер додатково перевіряє заголовок `Origin`.
Чужий сайт його не підробить: браузер ставить його сам.

### 3.2 CSRF входу

**CSRF** — коли чужий сайт змушує твій браузер зробити запит від твого імені.
Вхідний варіант — «залогінити» жертву в акаунт зловмисника.
- `handoff` приймає **лише JSON**. HTML-форма на чужому сайті може надіслати
  тільки form-data, а JSON із чужого домену браузер без дозволу CORS не відправить.
- `poll` вимагає cookie-прив'язки, якої в жертви немає.

### 3.3 Ліміти запитів (rate limiting)

Алгоритм — **фіксоване вікно**: «не більше N запитів за 60 секунд на ключ».
- Ключ для анонімних маршрутів — **IP** (на сервері з заголовка Cloudflare, якому
  можна вірити, бо інших шляхів до API немає).
- Ключ для закритих маршрутів — **Telegram ID**, тож люди в одній церковній
  Wi-Fi не ділять ліміт між собою.

Ліміт «на людину» має стояти **після** перевірки входу, бо до неї невідомо, хто
це. Перша версія мала глобальний ліміт, який спрацьовував раніше за вхід, тож
режим «на людину» мовчки працював як «на IP». Аудит це знайшов. Тепер ліміт
стоїть на кожному маршруті у правильному місці, а якщо його поставити неправильно,
код падає з помилкою, а не мовчить.

Код: `api/src/shared/http/rate-limit.guard.ts`

### 3.4 Заголовки безпеки

API (`api/src/shared/http/security-headers.ts`):

| Заголовок | Навіщо |
|---|---|
| `Cache-Control: no-store` | Відповіді не зберігаються ні в браузері, ні в Cloudflare |
| `X-Content-Type-Options: nosniff` | Браузер не «вгадує» тип файлу (захист від підсовування скриптів) |
| `X-Frame-Options: DENY` + CSP `frame-ancestors 'none'` | Сторінку не можна вбудувати в чужий сайт (clickjacking) |
| `Content-Security-Policy: default-src 'none'` | API — це дані, тож жодних скриптів чи стилів |
| `Referrer-Policy: no-referrer` | Адреса сторінки не передається іншим сайтам |
| `Strict-Transport-Security` | Браузер запам'ятовує «тільки HTTPS» на рік |

Сайт (`public/_headers`, Cloudflare застосовує сам): CSP дозволяє скрипти лише
з нашого домену, запити лише до нашого API, і забороняє вбудовування.

### 3.5 Одноразове посилання в `#`

Частина адреси після `#` (fragment) **не надсилається на сервер**, тож не
потрапляє в логи Cloudflare. Тому токен у посиланні від бота стоїть як `#t=…`.
Сайт читає його JavaScript-ом і одразу прибирає з адресного рядка.

## 4. Дані

### 4.1 Де лежать закриті дані

**Тільки** в SQLite на сервері. Їх немає:
- у git: інакше вони були б назавжди в історії й на GitHub;
- у Docker-образі: образ можна скачати;
- у фронт-бандлі: його отримує кожен відвідувач.

Сайт отримує дані лише запитом після всіх перевірок. Між базами вони
переносяться через **пайп** (`export | ssh … import`), тож файл ніде не
створюється.

### 4.2 Розділення оточень

На dev і local лежать **вигадані** дані (`pnpm private:demo`), реальні — тільки на prod.
- `demo` відмовляється працювати на prod (інакше затерло б реальний звіт).
- `import` реальних даних відмовляється працювати на dev і local.

Менше місць із реальними даними — менше місць, звідки вони можуть витекти.

### 4.3 `pnpm db`: принцип найменших прав

- Без `--write` база відкривається **лише для читання** на рівні SQLite. Навіть
  хитрий запит (`WITH … DELETE`) не спрацює.
- З `--write` можна змінювати дані, але не журнали й не таблицю міграцій.
- SQL передається через stdin, а не через аргументи, бо аргументи видно в
  списку процесів (`ps`).

## 5. Журнали: як довести, що сталося

### 5.1 Два журнали

| Журнал | Що пише | Навіщо |
|---|---|---|
| `report_views` | Хто відкривав звіт: ID, час, IP, пристрій | Знайти джерело витоку (`pnpm views`) |
| `security_events` | Входи, відмови, неправильні числа, ліміти, «Це не я» | Помітити атаку (`pnpm db`, запит у telegram-auth.md) |

Обидва живуть 180 днів і чистяться автоматично (`RetentionService`).
Безстрокове зберігання IP — це і ризик приватності, і порушення принципу
мінімізації даних.

### 5.2 Тригери в базі: захист на рівні SQLite

Навіть якщо оминути наші скрипти, сама база не дасть:
- змінити будь-який запис журналу (`BEFORE UPDATE … RAISE(ABORT)`);
- видалити записи, молодші за 30 днів.

> Чесна межа: людина з повним доступом до файлу бази може видалити тригер і
> змінити журнал. Від цього захищає лише копія журналу **поза** сервером
> (зовнішнє сховище логів). Це наступний крок, коли воно з'явиться.

Код: `api/migrations/0014_security_hardening.sql`,
`api/src/shared/log/security-log.service.ts`

## 6. Відстеження витоків (скріншоти)

Браузер **не дає** сайту ні заборонити скріншот, ні дізнатися про нього. Хто
обіцяє «захист від скрінів» на вебі, вводить в оману. Тому мета інша — зробити
витік **відстежуваним**:

| Прийом | Як працює |
|---|---|
| Плашка внизу екрана | «🔒 Переглядає ID … · час» закріплена, тож є на будь-якому скріні |
| Невидимий знак | Той самий текст на всьому звіті з прозорістю 2%. Оку не видно, а після підкручування контрасту проступає |
| Розмиття | Звіт розмивається, коли вкладка неактивна (перемикач застосунків, частина інструментів скріну) |
| Без копіювання й друку | Не виділяється текст, «Зберегти як PDF» дає порожню сторінку |

Час на плашці збігається із записом у `report_views`, тож скрін веде до
конкретної людини й конкретного перегляду.

Код: `src/widgets/report-view/ui/Protected.tsx`

## 7. Інфраструктура

### 7.1 Конфіг, який не дасть помилитись

`APP_ENV` = `local` | `dev` | `prod`. Якщо не задано, діють правила **prod** (fail
closed). На dev і prod сервер **не стартує**, якщо:
- cookie без `Secure`, без префікса `__Host-` або з `COOKIE_DOMAIN`;
- хоч одна адреса сайту не `https://`;
- `JWT_SECRET` коротший за 32 символи або схожий на заглушку.

Краще впасти при старті, ніж працювати небезпечно.

Код: `api/src/app/config/env.ts`

### 7.2 Docker

| Налаштування | Навіщо |
|---|---|
| Жодного порту назовні (dev/prod) | До API можна дістатись лише через Cloudflare-тунель. Повз WAF і ліміти Cloudflare не пройти, а IP у журналі не підробити |
| `read_only: true` | Файлова система контейнера лише для читання: зламаний процес не підмінить код |
| `cap_drop: [ALL]` | Процес не має жодних привілеїв Linux |
| `no-new-privileges` | Навіть через вразливість не можна підвищити права |
| `user: node` | Не root |
| Образи за хешем `@sha256:…` | Збирається саме той образ, який ми перевірили. Тег можна тихо перезаписати, хеш — ні |
| Ротація логів 5×10 МБ | Логи не заповнять диск |
| Секрети в `env_file`, не в образі | `.dockerignore` не пускає `.env` у збірку |

### 7.3 Секрети

- У кожного оточення свій бот, свій `JWT_SECRET`, свій тунель.
- Справжні `.env` у `.gitignore`, у git лише `*.example`.
- Токен, що засвітився будь-де (чат, скрін, лог), вважається скомпрометованим і перевипускається.

## 8. SOC 2 простими словами

**SOC 2** — це стандарт аудиту, а не сертифікат коду. Аудитор перевіряє, чи в
організації є **контролі** (правила + їх виконання) за п'ятьма критеріями:
безпека, доступність, цілісність обробки, конфіденційність, приватність. Код
покриває технічну частину. Решта — процеси: хто має доступ до сервера, як
навчають людей, що робити при інциденті.

| Контроль | Що означає | Що в нас |
|---|---|---|
| CC6.1 | Логічний доступ: хто що бачить | Вхід через Telegram + 4 перевірки на кожен запит |
| CC6.3 | Видача й відкликання доступу | Членство в каналі, «Вийти», «Це не я», відкликання адміном |
| CC6.6 | Захист периметра | Тунель, жодних відкритих портів, CORS/Origin, заголовки |
| CC6.7 | Захист даних у дорозі | Лише HTTPS, `Secure`, HSTS |
| CC7.1 | Виявлення вразливостей | Аудити коду, перевірки конфігу при старті, образи за хешем |
| CC7.2 | Моніторинг подій | `security_events` у SQLite, захищений тригерами |
| CC8.1 | Керування змінами | Тести (129) і smoke-тест; варто додати CI |
| C1.1 / C1.2 | Конфіденційність і знищення | Дані лише в SQLite, 180 днів для журналів |
| P4 | Мінімізація персональних даних | Не зберігаємо імен у журналах, лише Telegram ID |

**Що ще потрібно для справжнього SOC 2** (поза кодом):
- письмова політика доступу (хто має SSH до сервера);
- зашифровані бекапи бази за межами сервера;
- план реагування на інцидент (кого повідомити, як відкликати доступ);
- CI, що проганяє тести й `pnpm audit` на кожну зміну;
- зовнішнє сховище логів.

## 9. Як перевірити все самому

```bash
cd api && pnpm test                  # 129 модульних тестів
cd api && pnpm smoke                 # запускає справжній сервер і б'є по ньому запитами
pnpm views                           # хто відкривав звіт
pnpm db "WITH x AS (SELECT 1) DELETE FROM report_views"   # має впасти: база лише для читання
curl -sI https://api.ubc-military-fund.com/health         # подивитися заголовки безпеки
curl -s -o /dev/null -w '%{http_code}\n' https://api.ubc-military-fund.com/report/secret  # 401
```

Тести, які варто прочитати, щоб зрозуміти логіку:
- `api/src/entities/login-session/api/nonce.repository.spec.ts` — усі стани входу, «чужий браузер нічого не отримає»;
- `api/src/shared/log/security-log.service.spec.ts` — як база не дає змінити журнал;
- `api/src/app/config/env.spec.ts` — з якими налаштуваннями сервер відмовиться стартувати;
- `api/scripts/smoke.mjs` — перевірка заголовків, CSRF, прив'язки браузера на живому сервері.
